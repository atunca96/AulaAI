================================================================================
A. ROOT CAUSE, RANKED BY EVIDENCE
================================================================================

--------------------------------------------------------------------------------
A1. CONFIRMED — the detector's "is this a person?" test is CAPITALISATION, and
    capitalisation does not mean "proper noun" in the taught languages.
--------------------------------------------------------------------------------

render_contract.personal_name_tokens() classifies a stem token as a PERSON when
it is capitalised, >= 3 characters, not ALL-CAPS, and not already present in the
option/answer/taught-vocabulary set. That is the entire test. There is no other
signal.

Measured, on the deployed commit, with a textbook relative-clause item:

    stem                  : Das ist die Wohnung, ___ wir gemietet haben.
    names (alleged PEOPLE): ['wohnung']          <-- "apartment"
    options normalised    : ['die', 'der', 'das', 'den']
    answer_turns_on_form  : False
    options_are_gender    : False
    explicit_gender       : False
      explanation    : gender_hit=['feminine'] shared_with_names=['wohnung']
      explanation_tr : gender_hit=[]           shared_with_names=['wohnung']
    VERDICT               : 'answer depends on gender inferred from a personal name'

The rule fired because the rationale names "Wohnung" and says "feminine". No
person exists anywhere on the page. The detector believes a common noun is a
person because the orthography capitalises it.

This is not a German fact. It is an orthography fact, and it has TWO sides:

  OVER-FIRING. Same probe, same shape, other taught languages:

      admitted  names=['esta']             | Spanish
      admitted  names=['книга', 'это']     | Russian
      admitted  names=['αυτο', 'σπιτι']    | Greek
      REFUSED   names=['dit', 'woning']    | Dutch      <-- same defect, not German

    Spanish/Russian/Greek escaped only by luck: their antecedent noun happens to
    be lower-case in the stem, so it never becomes a "name" candidate. The
    moment a rationale cites a capitalised stem token — which includes the
    SENTENCE-INITIAL WORD OF EVERY STEM IN EVERY CASED SCRIPT — the same refusal
    appears. Demonstrated:

      stem "Casa es grande." + rationale "Casa is feminine, so «la»."
      -> 'answer depends on gender inferred from a personal name'

    So all 11 cased-script taught languages (en, es, de, fr, it, pt, ru, tr, nl,
    sv, el) are exposed; de and nl are exposed on every noun rather than only on
    the first word.

  UNDER-FIRING. The same test makes the rule completely inert where there is no
  letter case at all:

      names=[] verdict='' | Chinese
      names=[] verdict='' | Japanese
      names=[] verdict='' | Korean
      names=[] verdict='' | Arabic

    And a GENUINELY unsafe item in one of those scripts is admitted:

      prompt      田中さんは___です。
      options     女性 / 男性 / 学生 / 先生
      explanation "Tanaka is a woman's name, so the answer is 女性."
      -> hidden_world_reason() == ''      <-- SHOULD refuse, does not

    The learner-safety rule this whole subsystem exists to enforce does not
    function at all for 4 of the 15 taught languages. That is a second, silent
    production defect of the same root cause and should be tracked even though
    it is not what is blocking this build.

--------------------------------------------------------------------------------
A2. CONFIRMED — the repair CONTRACT and the detector's escape hatch are
    mutually unsatisfiable for 13 of the 15 taught languages.
--------------------------------------------------------------------------------

Every one of the three strategies is prompted, in substance, with:

    "make the required grammatical evidence explicit in the visible stem"

The detector's only corresponding escape is `explicit_gender`, computed as

    _V57_GENDER_WORDS.search(_fold(stem))  or  any(noun in stem for _V57_GENDER_NOUNS)

against a ~10-token lexicon that contains English, Turkish and Russian words
only. But the STEM IS IN THE TAUGHT LANGUAGE. Measured — the same item with the
gender stated explicitly in the stem, per language:

    escape_open=False  verdict=REFUSED   | German  (feminin)
    escape_open=False  verdict=REFUSED   | Spanish (femenino)
    escape_open=False  verdict=REFUSED   | French  (féminin)
    escape_open=False  verdict=REFUSED   | Italian (femminile)
    escape_open=False  verdict=REFUSED   | Russian (женский род)
    escape_open=False  verdict=REFUSED   | Swedish (femininum)
    escape_open=True   verdict=admitted  | English (feminine)
    escape_open=True   verdict=admitted  | Turkish (dişil)

The escape opens ONLY for the two INSTRUCTIONAL track languages. For a course
whose taught language is anything else, a model that follows the repair
instruction perfectly still cannot clear the blocker. The better the model
complies, the more certainly it is refused.

THIS IS THE CONTRACT MISMATCH YOU ASKED FOR. It is not a control-flow bug, not a
field-resolution bug, and not a bad model candidate. The repair surface and the
acceptance predicate disagree about what counts as evidence, and the
disagreement is structural.

--------------------------------------------------------------------------------
A3. CONFIRMED — the dependency gate that was supposed to prevent exactly this
    over-firing is a no-op for grammar items.
--------------------------------------------------------------------------------

_name_gender_rationale() only fires when the gender claim could actually decide
the answer. Three routes:

    (1) options are a form paradigm      -> False here ('die/der/das/den':
                                            shared prefix < 3, not a paradigm)
    (2) two options are gender values    -> False here (relative pronouns)
    (3) the statement names the keyed answer -> TRUE

Route (3) is satisfied by any rationale that quotes its own answer — which every
competently written grammar rationale does ("... so «die»"). So the safety net
that keeps this rule off ordinary grammar content is open by construction for
precisely the class of item that trips A1.

--------------------------------------------------------------------------------
A4. CONFIRMED — the quoted-vocabulary escape is case-gated, so it cannot help
    a language that capitalises its nouns.
--------------------------------------------------------------------------------

_quoted_common_tokens() deliberately keeps CAPITALISED quoted tokens as name
candidates (so that a rationale citing 'Анна' is still caught). In a language
whose common nouns are capitalised, quoting the vocabulary — «Wohnung» — does
not exempt it. Measured:

    REFUSED | rationale quotes the antecedent: "The antecedent «Wohnung» is feminine..."

So the one idiom a model would naturally reach for ("cite the word, don't name a
person") is unavailable in exactly the languages that need it.

--------------------------------------------------------------------------------
A5. RULED OUT — hypotheses that are NOT the cause.
--------------------------------------------------------------------------------

  * NOT the convergence loop. Already fixed by 321f7aec; strategies_tried=3 is
    a finite, correct exhaustion.
  * NOT locale stem-alias mismatch. a5f9a3ea was a real architectural risk and
    was correctly fixed, but the detector reads _v57_stem() (a single
    first-non-empty field) and the refusal reproduces with a single `prompt`
    field present, so alias divergence is not required to produce it.
  * NOT a bad model candidate. Three different prompts and models produce the
    same outcome, and the failure reproduces deterministically with NO model in
    the loop at all — the probe above is pure predicate evaluation.
  * NOT the rescue being model-trusted. Inspected: the rescue deep-copies,
    applies, runs R.repair_lesson, _audit_topic, _topic_render_blockers and
    _explanation_grounding_blockers, and commits only if all clear. It is
    architecturally sound. It returns 0 because the SAME wrong predicate gates
    it. A validator-proven repair cannot outrun a wrong validator.
  * NOT normalisation undoing the repair. R.repair_lesson is idempotent text
    normalisation; the refusal is present before and after it.
  * NOT the immutable answer/options/distractors tuple. See F.

    def explain_hidden_world(page: Dict[str, Any]) -> Dict[str, Any]:
        """Every input the hidden-world predicate used, and what it concluded.

        Pure. No side effects. Used by the gate's failure path and by tests.
        """
        stem_v57 = _v57_stem(page)
        names = personal_name_tokens(page, stem_v57)
        folded_stem = _fold(stem_v57)
        out = {
            "mcq_like": mcq_like(page),
            "stem_v57_field": next(
                (k for k in _V57_STEM_KEYS
                 if isinstance(page.get(k), str) and page.get(k).strip()), None),
            "stem_v57_value": stem_v57,
            "stem_tr_resolved": resolve_stem(page, True),
            "stem_en_resolved": resolve_stem(page, False),
            "name_candidates": sorted(names),
            "lexical_tokens": sorted(_lexical_tokens(page))[:40],
            "options_normalised": _normalised_options(page),
            "answer_turns_on_form": answer_turns_on_form(page),
            "options_are_gender_values": _options_are_gender_values(
                page, _V57_GENDER_WORDS),
            "explicit_gender_escape": bool(_V57_GENDER_WORDS.search(folded_stem))
                or any(n in folded_stem for n in _V57_GENDER_NOUNS),
            "explanations": {},
            "verdict": hidden_world_reason(page),
        }
        answer_tokens = set(_WORD_TOKEN.findall(_fold(page.get("answer"))))
        for key in _V57_EXPLANATION_KEYS:
            text = page.get(key)
            if not isinstance(text, str) or not text.strip():
                continue
            per_statement = []
            for statement in _STATEMENT_SPLIT.split(text):
                f = _fold(statement)
                toks = set(_WORD_TOKEN.findall(f))
                per_statement.append({
                    "statement": statement.strip()[:160],
                    "gender_hits": _V57_GENDER_WORDS.findall(f),
                    "name_word_hits": _V57_NAME_WORDS.findall(f),
                    "shared_with_name_candidates": sorted(toks & names),
                    "names_the_keyed_answer": bool(
                        answer_tokens and answer_tokens <= toks),
                    "quoted_common": sorted(_quoted_common_tokens(statement)),
                })
            out["explanations"][key] = per_statement
        return out

  * s2/s3/s4 fields DIFFER from s1 but hidden_world.verdict is unchanged
        -> the repair wrote to the right place and the PREDICATE is wrong.   (A1/A2)
  * s2/s3/s4 fields IDENTICAL to s1
        -> the model returned a no-op; look at candidate.rejected logs.
  * s2/s3/s4 clean but s5 (post-normalisation) refuses again
        -> normalisation reintroduces it; inspect R.repair_lesson.
  * stem_v57_field differs from the field the repair wrote
        -> field-resolution mismatch; the repair is editing a field the

================================================================================
E. ANSWERS TO THE SPECIFIC QUESTIONS
================================================================================

1. WHAT RUNTIME STATE TO INSPECT NEXT
   The live pages[4] row (section C). Specifically name_candidates and, for each
   rationale statement, shared_with_name_candidates + gender_hits. Nothing else
   is needed to close this.

2. WHICH FUNCTIONS TO INSTRUMENT
   render_contract.personal_name_tokens, _name_gender_rationale,
   hidden_world_reason (via the single explain_hidden_world wrapper);
   quality_gate.converge_topic (per-round, before/after dispatch),
   _repair_name_gender_page_exact, _repair_topic_render_stems_exact,
   _strategy_render_rescue (candidate rejection paths).

3. WHAT TO LOG BEFORE/AFTER EACH STRATEGY
   Before: page_digest, full field map, stem_v57_field/value, resolved TR+EN
   stems, name_candidates, dependency-route booleans, verdict.
   After:  the strategy's return value, the candidate `updates` map, and the
   candidate probe's explain_hidden_world(). The after-candidate dump is what
   separates "bad sentence" from "unsatisfiable predicate".

4. WHERE THE OFFENDING TEXT LIVES — how to prove it
   It is not "offending text" at all; it is an offending CLASSIFICATION of
   ordinary text. Proof procedure: take name_candidates, and for each token ask
   whether it appears lower-cased anywhere in the taught-language material
   (vocabulary tables, other stems, glossary). A token that appears lower-cased
   elsewhere is a common noun, not a name. In the reproduction, 'wohnung' is the
   antecedent of the relative clause, present in the stem, and the rationale must
   cite it. If instead name_candidates were EMPTY and the verdict still fired,
   the cause would be the name-word fallback branch, and the log's
   name_word_hits field would show it.

5. BAD CANDIDATE vs WRONG FIELD vs LATER NORMALISATION
   Use the s0..s5 table in D. Concretely, all three are already excluded here:
   - wrong field: excluded, the refusal reproduces with a single `prompt` key;
   - normalisation: excluded, the refusal is present before R.repair_lesson;
   - bad candidate: excluded, the refusal reproduces with NO model in the loop.

6. IS THE IMMUTABLE answer/options/distractors TUPLE THE BLOCKER?
   NO. This is important and it is measured, not assumed. Holding the tuple
   fixed, three of six candidate rewrites were ADMITTED:

       REFUSED  | original
       REFUSED  | rationale quotes the antecedent
       admitted | rationale avoids naming the antecedent
       admitted | stem states the gender explicitly (+ rationale avoids it)
       admitted | rationale cites the article instead
       admitted | no gender vocabulary at all

   So the item is satisfiable. But look at WHAT satisfies it: every admitted
   variant works by REFUSING TO SAY WHICH WORD GOVERNS THE AGREEMENT — which is
   the entire pedagogical content of a relative-pronoun item. The predicate is
   therefore not making the item impossible; it is making the item impossible TO
   EXPLAIN CORRECTLY. Do not relax the immutable tuple: that would be fixing the
   wrong thing, and it would let a repair silently change what the item tests.

7. THE CORRECT GENERIC POLICY
   Not "regenerate the page", not "allow tuple repair", not "swap in another
   item". Those all presuppose the item is defective. It is not. The correct fix
   is to make the predicate mean what it says:

   (i)  A name candidate must be evidenced as a PROPER noun, not merely
        capitalised. Language-agnostic signals available today, no lexicon:
          - the token also occurs LOWER-CASED elsewhere in the same topic
            (vocabulary rows, other stems, glosses) -> it is a common noun;
          - the token is capitalised in NON-sentence-initial position;
          - the token is absent from the topic's taught-vocabulary inventory.
        Cheap, and it removes 'wohnung' and every sentence-initial artefact in
        all 11 cased-script languages at once.

   (ii) Replace the `explicit_gender` stem lexicon with a language-agnostic
        test. The claim "the evidence is visible" is really "the rationale's
        gender claim is anchored to a token the STEM shows". Compare the
        rationale's cited token against the stem rather than matching an EN/TR
        word list against a taught-language stem. This closes A2 for all 15.

   (iii) Close the route-3 hole in the dependency gate: a rationale naming the
        keyed answer is NOT evidence that a person's gender decides the answer;
        it is the normal shape of every grammar rationale. Route 3 should
        require the answer AND a name candidate in the same statement, not the
        answer alone.

   (iv) Fix the under-firing half (Chinese/Japanese/Korean/Arabic). Since
        capitalisation carries no information there, name detection must fall
        back to a script-independent signal — e.g. a token in the stem that the
        rationale asserts a gender about AND that appears in no taught-vocabulary
        inventory. Same predicate, no per-language branch.

   Only after (i)-(iii) should anyone ask whether a strategy is missing. My
   expectation is that render_name_gender alone will clear this page once the
   predicate stops refusing correct content, and that render_rescue becomes
   dead weight for this class.

8. MAKING IT APPLY TO ALL 15 LANGUAGES
   Every signal in (7) is computed from the page's own fields and the topic's own
   vocabulary inventory — relative evidence, not absolute word lists. Gate the
   change behind a regression matrix that runs the SAME item shape in, at
   minimum: German and Dutch (noun capitalisation), Spanish/French/Italian/
   Portuguese/Swedish/Greek/Russian (sentence-initial capitalisation), Turkish
   and English (instructional tracks, where the current escape works and must
   keep working), and Chinese/Japanese/Korean/Arabic (no case — must start
   REFUSING the genuinely unsafe item shown in A1). Assert both directions:
   the grammar item is admitted, the name-inference item is refused.


================================================================================
F. SUMMARY
================================================================================

The three strategies do not fail because they are weak, mis-routed, or
model-limited. They fail because they are all gated by one predicate that is
wrong in a way no rewrite can satisfy:

  * personal_name_tokens() equates CAPITALISATION with PERSONHOOD. In a language
    that capitalises common nouns, the antecedent of a relative clause is
    classified as a person; in every cased script, so is the first word of every
    stem.
  * The repair contract instructs the model to make grammatical evidence
    explicit in the stem, while the detector's only "evidence is explicit"
    escape matches an English/Turkish/Russian word list against a stem written
    in the TAUGHT language. Measured: the escape is reachable in 2 of 15
    languages.
  * The dependency gate that should have prevented the over-firing is opened by
    any rationale that quotes its own answer — i.e. by every correct grammar
    rationale.

Consequence: a correct, well-grounded item is refused, and the only rewrites
that pass are ones that omit the grammatical explanation the item exists to
teach. The rescue's validator-proof behaves exactly as designed and returns 0
every time, because a validator-proven repair cannot outrun a wrong validator.

Same root cause, opposite sign: the rule is inert in Chinese, Japanese, Korean
and Arabic, where a genuinely unsafe name-inference item is currently admitted.

Fix the predicate. Do not add a fourth strategy, do not relax the immutable
tuple, and do not weaken the renderer rule.
